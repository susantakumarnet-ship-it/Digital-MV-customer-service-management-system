# Solution Architecture

**Project:** Digital MV Customer Service Management System
**Status:** Phase 1 draft, awaiting project-owner acceptance

## 1. Overview

```
 Browser (desktop / tablet / phone)
   │  HTTPS
   ▼
 Reverse proxy / load balancer (TLS, HSTS, gzip)
   ├── /            → React SPA (static build, served from a CDN or nginx)
   └── /api/v1/*    → Node.js API (stateless; one or more instances)
                         │
        ┌────────────────┼────────────────────┬─────────────────────┐
        ▼                ▼                    ▼                     ▼
   MongoDB replica    Private object      Email provider       Optional SMS /
   set (data,         storage (S3-        (SMTP / API)         WhatsApp adapter
   counters, jobs)    compatible)
```

- **One codebase, three environments.** Development, staging/UAT and production differ only in their environment variables.
- **The API is stateless.** Sessions are refresh tokens stored in MongoDB, so the API can run as several instances. Scheduled jobs use a lock held in MongoDB, so only one instance runs each job.
- **Every business rule lives in the backend.** The frontend's route guards and hidden buttons exist for usability, not security.

## 2. Technology choices

| Concern | Choice | Reason |
|---|---|---|
| Monorepo | npm workspaces: `apps/api`, `apps/web`, `packages/shared` | One install. Shared types, permission keys, status enums and Zod schemas mean client and server validate the same way. |
| Backend | Node.js 24 LTS, TypeScript, **Express 5** | Small and well understood. NestJS was considered: it would add ceremony without adding capability we need. Each module is laid out the same way (`routes → controller → service → model`). |
| Validation | **Zod**, with OpenAPI generated by `@asteasolutions/zod-to-openapi` | One schema covers request validation, TypeScript types and the API docs. |
| Database | **MongoDB 7+ (9.0 locally)** with **Mongoose 8** | As specified. Transactions need a replica set (see D-27). |
| Password hashing | **Argon2id** (`@node-rs/argon2`) | Ships prebuilt binaries, so there are no native-build problems on Windows. |
| Auth tokens | JWT access token (15 min, kept in memory) and an opaque refresh token (HttpOnly, Secure, SameSite=Strict cookie, rotated on every use, stored hashed) | Supports logout, revocation, and detecting a reused refresh token. |
| MFA | TOTP (`otplib`) with recovery codes | D-21 |
| File storage | A `StorageProvider` interface with an **S3-compatible** adapter (AWS S3, MinIO, Azure through its S3 gateway, and others) and a **local private-disk** adapter for development | Signed, time-limited download URLs. Raw storage paths are never exposed. |
| Uploads | `multer` (memory, size-capped), `file-type` for magic-byte checks, an optional ClamAV hook | HO §7.1 |

| Exports | `exceljs` (XLSX), `fast-csv` (CSV), `pdfkit` (PDF) | No headless browser needed in production. |
| Logging | `pino` (JSON) with a request ID on every line | |
| Error tracking | Sentry SDK, optional (enabled when a DSN is set) | |
| Frontend | **React 18, TypeScript, Vite**, Tailwind CSS, **shadcn/ui** (Radix primitives), React Router 6 | Accessible primitives on a modern enterprise look that we can theme. |
| Data fetching | TanStack Query, with an Axios client that refreshes tokens | |
| Forms | react-hook-form with Zod resolvers, using the shared schemas | |
| Tables | TanStack Table (server-side pagination, sorting and filtering) | |
| Charts | Recharts | |
| Calendar | FullCalendar (MIT core) | For the assignment board's calendar view |
| Tests | **Vitest** and **Supertest** (API); `mongodb-memory-server` in **replica-set mode** (transactions); React Testing Library; **Playwright** (E2E, viewports, axe accessibility checks); **k6** (performance) | |
| Migrations | `migrate-mongo` | Versioned, reversible scripts |
| CI/CD | GitHub Actions: lint → typecheck → test → `npm audit` and secret scan → build → Docker image → deploy to staging → **manual approval** → production | D-10 decides where it deploys. |
| Packaging | Dockerfiles for the API and web, plus `docker-compose` for a production-like local stack | Docker is not installed on this machine. It is only needed for deployment, not for development. |

## 4. Cross-cutting design

### 4.1 Authentication flow

1. `POST /auth/login` checks the password with Argon2id and enforces a lockout counter.
   - If the user has MFA, it returns `mfaRequired` and a short-lived challenge token.
   - Otherwise, it returns an access token in the response body and sets the refresh cookie.
2. `POST /auth/refresh` rotates the refresh token. If an old token is reused, the whole session family is revoked.
3. A CSRF double-submit token protects the cookie-authenticated endpoints (`/auth/refresh`, `/auth/logout`). All other APIs use a bearer token, which is not vulnerable to CSRF.
4. Deactivating a user revokes their sessions immediately.

### 4.2 RBAC and data scoping

Permission keys follow the pattern `module.action[.qualifier]`, for example:

- `complaint.read`, `complaint.classify`
- `workOrder.assign`
- `inspectionReport.approve`
- `material.issue`
- `ncr.verify`
- `report.export`
- `audit.read`
- `settings.administer`

Rules:

- Roles are collections of permission keys. The eight system roles are seeded and cannot be deleted. Admins can create custom roles.
- **Default deny:** each route names its required permission, and the `authorize()` middleware rejects any request that doesn't have it.
- **Scope:** each user has a scope of `organizationIds[]`, `regionIds[]` and `siteIds[]`, or `global`.
  - `ScopeService.filterFor(user, entity)` builds the MongoDB filter that every list, detail, report and export query uses.
  - Engineers are scoped further to work orders where `assigneeIds` contains their ID.
  - Customer users are scoped to their own organisation.
- **Separation of duties:** these checks live in the workflow guards rather than in the UI. For example, the reviewer cannot be the report submitter, and the approver cannot be the requester.

### 4.3 Workflow engine (state-transition service)

The engine stops anyone from setting a status directly. Each workflow is defined as data:

- A `workflowDefinitions` collection holds one definition per entity: complaint, workOrder, visit, inspectionReport, materialRequest and ncr.
- A definition lists the states (key, label, colour, whether terminal) and the transitions `{ from[], to, action, permission, requiredFields[], guards[], requiresReason }`.
- It is seeded from Appendix A and the BRF §22 lifecycle. Admins can change labels and toggle optional transitions.
- **Guards** are named functions registered in code, for example `intakeComplete`, `notSelfApproval`, `closureConditionsMet`, `timeSequenceComplete` and `issueWithinApproved`. The configuration can choose which guards apply, but it cannot inject logic.

`WorkflowService.transition(entity, id, action, payload, actor)` does the following:

1. Loads the record within the actor's scope.
2. Checks the permission, the current state, the required fields and the guards.
3. Applies the change and appends to the status history.
4. Writes the audit entry and emits domain events for notifications.

All of this happens **in one transaction**. If any check fails, the caller gets 409 or 422 with a machine-readable reason.

### 4.4 Audit

- `AuditService.record()` is called inside the same transaction as the change it records.
- The `auditLogs` collection is append-only. The application has no update or delete path for it, and in production the database user is granted insert/find only on that collection.
- Before and after values go through a redaction map, so password hashes, tokens and secrets are never stored.

### 4.5 Reference numbers

- The `counters` document has the key `{ key: 'complaint', year: 2026 }`. It is incremented with a single `findOneAndUpdate({$inc}, {upsert, returnDocument:'after'})`, which is atomic, and formatted from the numbering configuration as `MV-2026-000001`.
- Work-order, visit, material-request and NCR numbers use the same mechanism with different prefixes. The prefixes are in D-13.

### 4.6 Idempotency

- Clients send an `Idempotency-Key` header on critical writes: public complaints, time events, report submission, stock transactions and acceptance decisions.
- The `idempotencyKeys` collection stores the key, the actor, a hash of the request and the response. It has a unique index and a 24-hour TTL.
- A replay returns the original response. Sending the same key with a different payload returns 422.

### 4.7 Time tracking

- One sequence is one visit plus one engineer. The six event types have a fixed order, from 1 to 6.
- The insert sets `serverTimestamp = new Date()` on the server. `clientTimestamp` and GPS are kept only as diagnostic metadata.
- A unique index on `{visitId, userId, eventType}` makes duplicate events impossible, even under concurrent requests. The service also checks that the event is exactly `lastEvent + 1`.
- A correction is stored as a separate `timeCorrections` document. When approved, it sets `correctedTimestamp` on a correction overlay. The original `serverTimestamp` is never modified.
- Durations are calculated from the effective timestamps. Effective means the approved correction if one exists, otherwise the original.

### 4.8 Inspection reports and versioning

- `inspectionReports` has one document per revision, with a unique index on `{visitId, revisionNo}`.
- A draft can be edited. Submitting it freezes it, and the service refuses updates to any non-draft revision.
- A returned report gets a new draft revision, copied from the previous one, with the reviewer's item comments attached.
- The template is snapshotted into the report, so later template edits never change historical reports.

### 4.9 Inventory

- `stockTransactions` is an append-only ledger. Transaction types are RECEIPT, RESERVE, UNRESERVE, ISSUE, RETURN, DAMAGE and ADJUST.
- `stockBalances` is a projection keyed by `{itemId, warehouseId}`. It is updated in the same transaction as the ledger entry, and a conditional update prevents a negative balance.
- A nightly job rebuilds the balances from the ledger and reports any drift.

### 4.10 Files

- An `attachments` collection holds the owner entity, uploader, original name, detected MIME type, size, SHA-256 hash, storage key and scan status.
- `GET /files/:id/url` checks the caller's scope against the owning entity, then returns a URL valid for 5 minutes.

### 4.11 Notifications

- A domain event (for example `workOrder.assigned`) goes to `NotificationService`. The service resolves the recipients, applies each user's preferences, renders the template, and writes `notifications` documents for each channel.
- A worker sends email, SMS and WhatsApp messages with retry and backoff, recording delivery status and failure reason.
- In-app notifications are read with polling, every 30 seconds by default. Server-Sent Events can be added later.

### 4.12 Customer acceptance tokens

- Each token is 32 random bytes. Only its SHA-256 hash is stored, alongside its purpose, its complaint, an expiry (7 days by default) and a used/revoked flag.
- `GET` shows the summary but changes nothing. Only `POST` with an explicit decision records acceptance. Each token can be used for one decision only.

### 4.13 Error format

```json
{ "error": { "code": "VALIDATION_FAILED", "message": "…", "fields": { "email": "Invalid email" }, "requestId": "…" } }
```

Stack traces are never returned. List responses use `{ data: [...], meta: { page, limit, total } }`, with `limit` capped at 100.

## 5. Data model

The design implements the 24 collections in BRF §19 and HO §8, using the fields and indexes from HO §8.2. It also needs these supporting collections:

| Collection | Purpose |
|---|---|
| `sessions` | Hashed refresh tokens, device and user-agent, expiry, revoked flag |
| `passwordResetTokens` | Hashed single-use reset tokens with a TTL |
| `cities`, `equipment`* | *Equipment is modelled as `assets` with an `equipmentTypeId`. D-04 confirms whether Asset and Equipment are separate levels. |
| `requestTypes`, `priorities`, `warehouses`, `notificationTemplates` | Master data |
| `workflowDefinitions` | State machines (§4.3) |
| `timeCorrections` | The correction workflow (§4.7) |
| `stockBalances` | Balance projection (§4.9) |
| `attachments` | File metadata (§4.10) |
| `idempotencyKeys` | §4.6, with TTL |
| `acceptanceTokens` | §4.12 |
| `jobLocks` | Scheduler leases |
| `exportJobs` | Asynchronous exports |

Embedded snapshots keep history accurate. For example, a complaint stores the site, asset and reporter names as they were at submission time, and a report stores its template snapshot.

## 6. Environments and configuration

| | Development | Staging / UAT | Production |
|---|---|---|---|
| Database | Local MongoDB (replica set, see D-27) | Managed replica set | Managed replica set with PITR backups |
| Storage | Local private folder (`./var/storage`, outside the web root) | S3-compatible bucket | S3-compatible bucket, private, versioned |
| Email | `.eml` files in `./var/mail` | Sandbox SMTP | Production SMTP/API |
| Seed data | Demo data | Anonymised UAT data | Roles and admin only |

Every setting comes from environment variables, which are validated at startup. The app refuses to start if a value is invalid or missing. Each app has a `.env.example`.

## 7. Phase gate procedure (every phase)

1. Implement the requirements mapped to the phase in the traceability matrix.
2. Run lint, typecheck and every test, and fix any failures.
3. Update the OpenAPI docs and the traceability status.
4. Write a phase demo script (step-by-step workflow walkthrough), and run it against the seeded environment.
5. Report the results, including open defects and new decisions, and wait for the project owner's acceptance.
